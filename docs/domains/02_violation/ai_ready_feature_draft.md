# 02 위반유형 AI Ready 피처 후보

작업 워크트리 `C:\mlo-03-p2-team2`, 브랜치 `codex/domain-02-sharing-ai-ready`.

첫 과제로 점검 직전 **해당 점검에서 FAIL이 나올지** 예측하는 안을 제안한다. 한 행은 예측 대상 점검 1건이며 `inspection_key`로 연결한다. 같은 사업장의 이력은 팀이 합의한 사업장 키로 모은다. 점검일만 있는 동안에는 현재 점검일보다 앞선 기록 중 예측 시점에 이용 가능했던 이력만 쓴다. 같은 날 여러 점검이 있어 시간 순서를 확인할 수 없으면 그날 기록은 제외한다. 현재 점검의 결과·위반 원문·위반 코드·후속 점검 정보는 입력 피처에서 제외한다.

| 후보 피처 | 계산 기준 |
| --- | --- |
| 직전 점검 위반 관측 상태 | 직전 점검의 `parsed`, `partial`, `raw_missing`, `unrecognized`. 과거 점검이 없거나 직전 점검을 하나로 특정할 수 없으면 사유를 구분한다. |
| 직전 점검에서 확인된 고유 코드 수 | 02 승인 코드 집합의 크기. `partial`은 확인된 최소 건수로 취급하고 관측 상태를 함께 제공한다. 직전 기록이 없거나 원문이 없거나 해석 불가면 결측으로 둔다. |
| 최근 365일 위반 코드가 확인된 점검 횟수 | 기준일 전 365일 동안 승인 코드가 1개 이상인 과거 점검 수. 이력 자체가 미확인인 경우 결측을 유지한다. 그 외 집계의 0은 해당 기간에 승인 코드가 확인된 점검이 0회라는 뜻이다. |
| 최근 365일 점검 횟수와 상태별 점검 횟수 | 위반으로 확인된 횟수와 함께 본다. 분모 후보인 과거 전체 횟수와 관측 상태별 횟수를 각각 보존한다. |
| 최근 365일 각 위반 코드가 확인된 점검 횟수 | 같은 점검의 같은 코드는 1회로 세고 `(code_system_version, violation_cd)`로 묶는다. 모델에 넣을 코드 목록은 학습 기간 자료로 정한다. |

자료는 01 점검 Silver의 점검 키·날짜, 02의 [승인 코드와 관측 상태](team_integration_schema_draft.md)를 사용한다. 사업장 매칭이 안 되는 행은 사유를 남긴다. 공란이나 부분 파싱의 정도가 시기 및 업종에 따라 다른지도 확인한다. 새 스냅샷으로 다시 계산할 때는 원천 SHA-256, 피처 규칙 버전, 기간과 기준 시각을 함께 기록한다.

## 구현 전에 팀이 정할 사항

1. **정답과 모집단.** 점검 직전 FAIL 예측과 다음 점검의 동일 코드 재발 예측 중 첫 과제를 정한다. FAIL 예측은 `PASS W/ CONDITIONS`와 미평가 결과의 처리 방식을 확정한다. 재발 예측이면 비교 기간과 미관측·부분 관측의 분모를 03과 합의한다.
2. **사업장과 이력.** 같은 사업장을 판별할 키, 면허 재발급·주소 변경·복수 매칭 처리, 365일 범위, 위반 기록이 실제 이용 가능해진 시각을 정한다. 갱신 시각을 확인하기 어려우면 과거 날짜 필터의 한계를 기록한다.
3. **관측 상태와 코드 버전.** 부분 파싱에서 확인된 코드의 활용 범위, 코멘트 구분자가 없는 조각의 인정 여부, 코드 체계 변경 전후의 매핑 여부를 03·05와 정한다.
4. **검증 기간.** 시간순으로 학습·검증·테스트를 나누고 학습 기간 안에서만 결측 처리와 코드 목록을 정한다. 특정 날짜 뒤의 기록을 바꿔도 이전 날짜 피처가 그대로인지 확인한다.

합의 전 02에서 할 수 있는 검토는 사업장 키 후보별 매칭률, 과거 관측 상태 분포, 날짜 경계에서 피처가 달라지는 사례 확인이다.
