# 시카고 식품위생 점검·사업체 인허가 통합 분석 기획

## 목표와 범위

시카고시 식품위생 점검, 사업체 인허가, 커뮤니티 지역 경계 데이터를 연결합니다. 어떤 유형의 점검에서 불합격과 위반이 발생하는지, 같은 사업장에서 얼마나 반복되는지, 지역·인허가 이력에 따라 점검 결과가 어떻게 다른지 분석합니다. 검증된 점검 이력으로 예측 시점을 지키는 AI 학습용 데이터셋을 설계하는 것도 프로젝트 범위에 포함됩니다.

초기 공용 저장소에는 원천 설정, 폴더 구조, 작업 규칙과 이 기획서를 둡니다. 상세 데이터 모델, 지표 정의, 분석 코드와 검증 문서는 각 관점의 작업과 팀 리뷰를 거쳐 추가합니다.

## 원천 데이터

| 원천 | 공유 스냅샷의 규모 | 분석에서의 역할 |
| --- | ---: | --- |
| `food_inspections.csv` | 318,552행 | 점검 결과, 위반 텍스트, 일자와 좌표. [시카고시 Food Inspections](https://catalog.data.gov/dataset/food-inspections) |
| `business_licenses.csv` | 1,212,132행 | 인허가 발급·갱신·상태와 유효기간. [시카고시 Business Licenses](https://catalog.data.gov/dataset/business-licenses) |
| `community_areas.geojson` | 77개 지역 | 점검 위치의 커뮤니티 지역을 파악하는 경계. [시카고시 Boundaries – Community Areas](https://catalog.data.gov/dataset/boundaries-community-areas) |

팀은 Git의 `data/00_origin/`에서 원천 파일과 컬럼 설명 JSON을 받아 같은 스냅샷을 사용합니다. 용량이 큰 CSV 두 개는 분할 파일을 복원한 뒤 읽습니다. [원천 복원과 검증](project_setup_and_sharing.md#팀-공용-원천)

## 다섯 가지 분석 관점

| 번호 · 폴더 | 분석 질문 | 첫 산출물 |
| --- | --- | --- |
| `01_inspection` | 업종·위험등급·점검 유형별 결과는 어떻게 다른가? | 월별 점검 건수와 결과별 비율 |
| `02_violation` | 어떤 위반이 자주 나오며 분류 체계 변경은 비교에 어떤 영향을 주는가? | 위반 텍스트 구조화 결과와 분류 버전별 집계 |
| `03_repeat_inspection` | 같은 사업장에서 문제가 재발하는가? 후속 점검 결과는 어떻게 달라지는가? | 사업장별 과거 이력과 후속 점검 통계 |
| `04_license` | 점검 당시의 면허 이력을 어디까지 연결할 수 있는가? | 점검일 기준 인허가 매칭 결과와 후보 수 |
| `05_geospatial` | 지역·월·시설 유형별 점검 성과는 어떻게 다른가? | 지역별 위생점검 통계와 지도용 데이터 |

지역별 유효 인허가 사업장 대비 점검 범위는 04·05의 공통 확장 후보입니다. 두 관점의 기본 산출물을 검증한 뒤 범위를 정합니다.

## 파이프라인과 완료 기준

| 단계 | 목표 | 확인할 결과 |
| --- | --- | --- |
| Bronze | 원천 값과 기록 단위를 보존합니다. | 입력 스냅샷과 논리 레코드 수가 대조됩니다. |
| Silver | 날짜와 범주를 표준화하고 결측·이상값을 표시합니다. | 기본 레코드에서 원천 행을 일대일로 추적할 수 있습니다. |
| 데이터 품질 | 행 수, 키, 날짜 순서, 파싱과 매칭 결과를 검증합니다. | 실패·예외 사유와 결과에 미치는 범위가 기록됩니다. |
| Gold | 점검·위반·인허가 공통 모델을 구성해 관점별 분석에 사용합니다. | 각 테이블의 행 단위와 키가 명확하며 집계 중복을 검사합니다. |
| AI-Ready | 기준일 이전에 알 수 있었던 정보와 이후 실제 결과를 시간 순서에 맞게 구성합니다. | Feature와 Label의 기간을 대조하고 데이터 누수 여부를 검증합니다. |

구현은 원천 프로파일링, Bronze·Silver와 품질 검사, Gold 공통 모델과 관점별 분석, AI-Ready 검증 순서로 진행합니다. 기술 후보는 Python, DuckDB, Parquet, pytest이며 실제 원천에 대한 확인을 거쳐 조합을 확정합니다.

## 팀에서 결정할 항목

- 점검 결과 중 불합격률의 분모에 포함할 상태와 후속 점검을 연결하는 기준
- 면허번호와 사업장 키의 관계, 유효기간 경계, 점검 당시 후보가 여러 개인 경우의 처리
- 위반 분류 기준 변경 전후의 비교 범위와 파싱 실패 처리
- 좌표가 없는 점검, 경계에 걸린 위치, 표본이 적은 지역의 표시
- AI 학습용 기준일, Label 관찰 기간, 시간 순서에 맞춘 학습·검증 구간

팀원은 공용 초기 구조에서 관점별 브랜치를 열고 구현과 검증을 진행합니다. 합의가 필요한 항목은 근거와 영향을 같이 기록합니다. [공용 작업 규칙](../AGENTS.md) · [프로젝트 Wiki](https://github.com/encore-ai-campus/mlo-03-p2-team2/wiki)
