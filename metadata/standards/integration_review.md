# 점검·인허가 통합과 날짜 예외 검토

상태: **Silver 설계안, JOIN 미구현**. 원천 행·Bronze 값은 유지한다. 팀원 제안은 `data_integration_conventions.md`와 `04_license_proposal.md`에서 읽었다. 현재 프로젝트의 직접 측정은 [원천 프로파일](../source_profiles.md)을 따른다. 두 집계는 조건이 달라 같은 지표로 비교하지 않는다.

## 공통 키와 grain

| 입력/결과 | 한 행의 의미 | 식별·연결 후보 | 현재 근거 |
| --- | --- | --- | --- |
| 점검 원천·Bronze | 점검 1건 | `Inspection ID` → `inspection_key` | 318,552행, ID 고유 |
| 인허가 원천·Bronze | 인허가 기록 1건 | `LICENSE ID` → `license_event_key` | 1,212,132행, ID 고유; `ID` 중복 출현 252건 |
| 지역 원천·Bronze | 지역 Feature 1개 | `area_numbe` → `community_area_num` | 77개 고유 번호 |
| 기간 후보 파생 결과(예정) | 점검 × 후보 인허가 기록 | `inspection_key`, `license_event_key` | 원천 이력을 삭제·병합하지 않음 |
| 팀 제공 매칭 요약(예정) | 점검 1건 | `inspection_key` | 후보 수·상태를 점검 1건에 집계하는 제안 |

점검 `License #`와 인허가 `LICENSE NUMBER`는 공통 `license_number_key` **후보**다. 인허가 `ACCOUNT NUMBER` + `SITE NUMBER`는 사업장 키 후보이나 유일성·기간 안정성이 검증되지 않았다. 점검 주소·상호와 인허가 주소·상호는 같은 이름으로 표준화할 수 있어도 결합 결과에서는 출처 접두사를 유지한다.

## 두 가지 JOIN 조건과 서로 다른 측정값

| 방식 | 조건·처리 단계 | 0 후보 | 1 후보 | 2 이상 후보 | 상태 |
| --- | --- | ---: | ---: | ---: | --- |
| 1. 번호만 | 비공란 `License # = LICENSE NUMBER`; 유효기간 미적용 | 16,577¹ | 35,887 | 266,088 | **이 프로젝트에서 직접 측정** |
| 2. 번호+점검일 | 번호 일치, `시작일 ≤ 점검일 ≤ 만료일` 양쪽 포함 | 84,828 | 232,323 | 1,401 | **팀 문서에서 인용, 현 프로젝트에서 미재현** |

¹ 번호만 방식의 0 후보는 비공란 무매칭 16,558건과 번호 공란 19건을 합한 값이다. 두 방식 모두 분모는 점검 318,552건이다. 팀의 기간 결과는 이 프로젝트의 코드를 실행해 검증한 수치가 아니다. 번호만 연결하면 인허가 이력 때문에 점검 266,088건에서 복수 후보가 나오는 반면, 기간 조건을 더하면 팀 문서상 1,401건이 된다. 집계 차이를 오류나 개선 효과로 단정하지 않는다.

팀 제안의 `License #=0` 840건, `9999999` 1건은 원천에서 읽기 전용으로 확인했다. 이 값의 무효 처리 여부에 따라 위 표가 달라질 수 있으므로, **원문은 유지**하고 별도 판정 규칙을 승인받기 전까지 현재 측정치를 덮어쓰지 않는다. 팀 기간 집계가 이 sentinel을 어떻게 처리했는지와 원천 SHA-256·실행 코드·날짜 예외 규칙을 받아야 같은 조건으로 재현할 수 있다.

## 기간 후보와 예외 상태 제안

1. 점검일·시작일·만료일의 **원문 문자열, 달력 파싱 여부, 업무 유효성**을 각각 남긴다. 숫자처럼 보이는 허가번호도 문자열로 유지한다.
2. 기간 후보는 번호가 일치하고 세 날짜가 사용 가능하며 `term_start_date ≤ inspection_date ≤ term_end_date`일 때만 센다. 시작/만료 공란, 역전, 업무 미확정 특이 연도는 원천 행을 버리지 않고 `period_ineligible_reason`으로 구분한다. 이 제외 규칙과 종료일 포함 여부는 **미확정**이다.
3. 후보 0건은 `blank_license_number`, `sentinel_under_review`, `number_not_found`, `period_not_covering_inspection`, `invalid_or_missing_period` 등 사유 후보를 구분한다. 한 행에 여러 사유가 가능할 때 우선순위는 팀 합의가 필요하다.
4. 후보 1건일 때만 `matched_license_event_key`를 채우는 안을 검토한다. 2건 이상은 `candidate_count_num`과 원본 후보 목록을 보존하고 임의로 최신 기록을 선택하지 않는다. `match_status_cd`와 분석 포함 여부는 팀 코드표에 등록해 확정한다.
5. 점검 단위 결과는 318,552행을 유지하는지, 인허가 기록 단위는 1,212,132행을 유지하는지, 후보 파생 행의 grain과 JOIN 전후 행 수가 맞는지 검증한다. 미매칭·복수 후보는 별도 품질 지표로 공개한다.

## 날짜 표준과 호환성

| 검사항목 | 확인된 사실 | 예정 처리·결정 상태 |
| --- | --- | --- |
| 원천 형식 | CSV 날짜 9개 컬럼의 비공란 값은 `MM/DD/YYYY` 달력 파싱 실패 0건 | 원문 별도 보존, Silver `date32` 후보, 표시 `YYYY-MM-DD` |
| `08/17/0206` | 인허가 만료일 1건. Python 날짜·Arrow `date32` 파싱 가능 | **업무상 유효성 미확정**. 2026으로 추측 보정 금지; 기간 후보 사용 보류안 |
| `01/01/9999` | 인허가 만료일 1건. Python 날짜·Arrow `date32` 파싱 가능 | sentinel 의미 **미확정**. 무기한 유효로 자동 해석 금지; 기간 후보 사용 보류안 |
| Pandas 변환 | 현재 환경에서 Pandas 미설치 | Pandas 날짜 타입으로의 왕복·범위 호환성 **미검증**; 구현 전 별도 검사 |
| GeoJSON 시스템 시각 | `:created_at`, `:updated_at`은 UTC 밀리초 표기 | `timestamp[ms, UTC]` 후보; 업무 경계 유효기간으로 사용하지 않음 |

`date32`에 담을 수 있음과 업무적으로 유효함은 다른 판정이다. 변환 실패는 `parse_failed`, 조사 범위 밖이지만 파싱 가능한 값은 `business_review`처럼 분리하는 안을 팀 코드 상태와 함께 확정해야 한다. 원본 `08/17/0206`, `01/01/9999`와 현재 프로파일의 건수는 수정하지 않는다.

## Gold 설계에 넘길 계약

향후 관점별 제시안은 분석 질문, 원천·스냅샷, 각 입력·출력의 grain, 연결 키와 시점, 공통 제공 컬럼, 미매칭·중복 처리, 품질 검증 기준과 실제 결과, 팀 합의 항목을 적는다. 04번의 `inspection_key`, `candidate_count_num`, `match_status_cd`, `matched_license_event_id`는 **팀 제안 컬럼**이며 확정 스키마가 아니다. `license_event_key`와 `matched_license_event_id`의 명명 차이도 통일해야 한다. 현재 Gold 모델은 만들지 않는다.
